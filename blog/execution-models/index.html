Synchronous, Asynchronous, Multithreading, and Multiprocessing

Nikhil Shinde|April 2, 2026|7 min read

Four execution models, the pain each one solves, and the tradeoffs hidden behind concurrency and parallelism.

Synchronous execution, asynchronous execution, multithreading, and multiprocessing are often discussed as if they are interchangeable ways to make software faster. They are not. Each model responds to a different pain point, and each introduces a different kind of complexity.

The first question should not be “Which one is fastest?” It should be:

Is the program spending its time waiting for something, or using the CPU to do work?

  • I/O-bound work spends time waiting for a network, disk, database, or user input.
  • CPU-bound work spends time computing: parsing, encoding, rendering, searching, or running an algorithm.

That distinction makes the four models much easier to understand.

1. Synchronous execution

In the synchronous model, one task runs after another on a single thread. When the current task starts an I/O operation, that thread waits until the operation completes.

The model is easy to follow because execution order matches the order in the code. That simplicity is valuable: errors are easier to trace, state changes are predictable, and debugging usually has a clear path.

The pain point: blocking

The problem appears when a slow operation sits in the middle of a critical thread. Imagine a UI thread making a network request synchronously. Until the server responds, the same thread cannot process clicks, redraw the screen, or respond to the user. The application looks frozen even if the CPU is mostly idle.

Synchronous execution is a good fit when:

  • operations are short;
  • later steps genuinely depend on earlier results;
  • simplicity matters more than throughput;
  • blocking does not affect other useful work.

It becomes painful when unpredictable I/O holds up everything behind it.

2. Multithreading

Multithreading creates multiple threads inside one process. If one thread is waiting, another can continue. Because the threads belong to the same process, they share memory and resources.

Sharing memory makes communication fast, but it also creates the central difficulty of multithreading.

The pain point: shared mutable state

Two threads can read and modify the same value at nearly the same time. The result may depend on timing, producing a race condition that disappears when a debugger is attached and returns in production.

Locks, mutexes, semaphores, and other synchronization tools can protect shared state, but they create new failure modes:

  • a missing lock can corrupt data;
  • too much locking can erase the performance benefit;
  • inconsistent lock ordering can cause a deadlock;
  • behavior can become difficult to reproduce and test.

SQLite is a good illustration of how deliberate this has to be. It ships three threading modes — single-thread (no locking at all), multi-thread (safe as long as no single connection is used by two threads at once), and serialized (safe to share everything) — and you pick one at compile time, at startup, or per connection. Thread safety is not a flag you flip; it is a contract the library and the caller have to agree on.

The hard part is never creating a thread. It is proving that shared state stays correct under every possible ordering.

One more thing that trips people up: more threads does not always mean more parallelism. Python's CPython runtime holds a global interpreter lock, so its threads interleave rather than run Python bytecode simultaneously — great for I/O-bound work, useless for CPU-bound work. JVM and Go threads do run on multiple cores. The runtime decides, not the keyword.

Multithreading works well when tasks benefit from shared memory and the state can be kept small, immutable, or rigorously synchronized.

3. Asynchronous execution

Asynchronous execution addresses waiting without requiring one application thread per task. A program starts an I/O operation, lets the operating system or hardware handle the wait, and continues doing other work. When the operation completes, the program is notified and resumes the dependent code.

Node.js is a familiar example. Its event loop can coordinate many in-flight I/O operations while JavaScript execution remains primarily single-threaded. This is especially effective for servers that spend much of their time waiting on sockets, databases, and files.

It is worth knowing what "the OS handles the wait" actually means, because it is not the same everywhere. Network sockets really are event-driven at the kernel level — epoll on Linux, kqueue on BSD, IOCP on Windows, io_uring more recently — so thousands of connections can be watched by one thread. Filesystem I/O generally has no such interface, so libuv fakes it with a small background thread pool. The API looks identical from JavaScript; the machinery underneath is not.

Callbacks were an early way to express this continuation. Deeply nested callbacks led to “callback hell,” where control flow and error handling became hard to see. Promises improved composition, and async/await made asynchronous code read more like synchronous code.

The pain point: hidden control flow

async/await improves readability, but it does not remove asynchronous complexity. Cancellation, timeouts, retries, partial failures, and concurrent operations still need deliberate handling. An accidentally omitted await or an unhandled rejection can create subtle bugs.

There is another important limit: async does not make CPU-heavy work disappear. If a single event-loop thread performs an expensive calculation, the loop cannot process other completions until that calculation yields or finishes.

Asynchronous execution is strongest when there are many independent I/O-bound tasks and relatively little CPU work between waits.

4. Multiprocessing

Multiprocessing launches multiple independent processes. Each process has its own memory space and runtime resources. This isolation avoids many shared-memory hazards and can use multiple CPU cores for genuine parallel work.

Consider brute-forcing a hash from a large dictionary or rainbow table. The input can be divided into chunks, with separate processes searching different sections at the same time. The same idea can extend across several machines.

The pain point: isolation has a cost

Processes do not naturally share memory. They exchange results through inter-process communication such as pipes, sockets, queues, or shared-memory regions. That means data may need to be serialized, copied, transferred, and reconstructed.

The tradeoffs include:

  • higher memory use than threads;
  • process startup and scheduling overhead;
  • explicit IPC and failure handling;
  • the need to divide work evenly;
  • more complicated coordination across machines.

Multiprocessing is usually the clearest choice for CPU-bound tasks that can be split into mostly independent units. It is less attractive when workers need constant access to a large, rapidly changing shared state.

Concurrency is not parallelism

These terms describe different properties:

  • Concurrency means making progress on multiple tasks during overlapping periods of time.
  • Parallelism means executing multiple tasks at the same instant, usually on multiple CPU cores.

Async code on one thread is concurrent but not necessarily parallel. Multiple processes on multiple cores can be both concurrent and parallel. Threads may be parallel, but the result depends on the runtime, operating system, and available cores.

ModelBest suited forMain advantageMain pain point
SynchronousSimple, ordered workPredictable control flowOne slow operation blocks progress
MultithreadingConcurrent work with shared stateCheap communication through shared memoryRaces, locks, and deadlocks
AsynchronousMany I/O-bound operationsHigh concurrency without a thread per taskComplex lifecycle and hidden control flow
MultiprocessingCPU-bound, divisible workIsolation and true multicore parallelismIPC, memory, and coordination overhead

A practical way to choose

Start with the simplest model that meets the requirement.

  1. Use synchronous execution when blocking is acceptable and clarity matters most.
  2. Use asynchronous execution when the bottleneck is waiting on many I/O operations.
  3. Use multithreading when shared-memory concurrency is valuable and the state can be made safe.
  4. Use multiprocessing when CPU-heavy work can be divided and isolation is worth the communication cost.

Real systems often combine them. A web server may use asynchronous I/O for thousands of connections, a thread pool for blocking libraries, and a process pool for CPU-heavy transformations. The goal is not to pick a winner. It is to put each kind of work into the execution model whose pain you can manage.
