Distrobox: Ubuntu Inside Bluefin Without Leaving Bluefin

I moved to an image-based OS, broke my whole dev workflow, and spent a month learning where development tools are actually supposed to live.

Nikhil Shinde/2026-04-09

Distrobox: Ubuntu Inside Bluefin Without Leaving Bluefin

A few weeks ago I wrote about what Docker is actually doing under the hood — chroot builds the walls, namespaces seal the ceiling and floor, cgroups control the air supply. I finished that post feeling like I finally understood containers.

Then I installed Bluefin, and containers stopped being a topic I read about and became the only way I could get work done at all.

This is the story of how that happened, because the useful part was not the final setup. It was the month of doing it wrong.

The day my OS said no

Bluefin is image-based. The operating system arrives as a composed, signed image, and /usr is read-only. You do not install the OS once and then slowly modify it for three years until nobody, including you, knows what is on it. You get the same image everyone else gets, and updates swap the whole thing atomically.

I understood that in theory. I did not understand what it meant on a Tuesday when I wanted to install a compiler.

My instinct was the instinct of every Linux user: install the package. On Bluefin that means rpm-ostree install, which does not install a package so much as compose a new system image with your package layered onto it. Which means:

rpm-ostree install thing
→ new deployment staged
→ reboot
→ now you have the thing

Reboot. To get a compiler.

I did it anyway, because I was stubborn. Then I needed a second tool. Reboot. Then a native library for a Python package. Reboot. Within a week I had a list of layered packages, and I had learned the part nobody warns you about: every layered package has to be re-applied on top of every new base image. My updates got slower. My system drifted further from the image everyone else was testing. I had taken a distribution whose entire value proposition was "the host is predictable" and spent seven days making my host unpredictable.

I was fighting the design. The design was not wrong.

The second wall: everything assumes Ubuntu

The other problem showed up at the same time and was more annoying, because it was nobody's fault.

Install instructions in the wild assume a mutable Debian-shaped machine. apt-get install. add-apt-repository. A curl | bash script that sniffs your distro, doesn't find one it recognizes, and either exits or — worse — guesses. Half the developer tooling ecosystem is written on the assumption that you have apt and root on a machine you are allowed to scribble on.

I had none of those things. I had a signed image and a read-only /usr.

The detour: I tried to solve it with a different distro

My first real fix was not a fix. It was a substitution.

I created an Arch container, because if my problem was "I need a mutable system with a real package manager," then obviously the answer was a mutable system with a very good package manager. The AUR has everything. Problem solved.

It was not solved. arch-box is still on my machine, and distrobox list reports it as Exited (0) 6 months ago, which is a polite way of saying I stopped opening it.

Two things went wrong. Arch was mutable, yes — but the install instructions I actually needed to follow were still written for Ubuntu, so I was translating package names by hand and guessing at library equivalents. And a rolling container that I only entered occasionally would drift, break on an update I hadn't run in a month, and cost me an afternoon I had planned to spend on the actual project.

The lesson took me embarrassingly long: I didn't want a better distro. I wanted the boring one that every install script was already written for.

That is when I made an Ubuntu box, and everything got quiet.

What Distrobox actually is

Distrobox creates a Linux distribution environment on top of an existing Linux host using a container engine — Podman in my case, running rootless.

Here is the part that connects straight back to the Docker post. Same kernel primitives. Same namespaces, same cgroups, same image-provides-the-root-filesystem model. Nothing new at the bottom of the stack.

What is different is the intent. In that post I described a container as a room: chroot builds the walls, namespaces seal the ceiling and floor, cgroups control the air supply. A service container wants that room sealed as tightly as possible — one process, one mounted directory, one published port.

Distrobox builds the same room and then deliberately knocks holes in the walls.

It connects the container to:

  • your home directory;
  • graphical display sockets for Wayland or X11;
  • audio through the host's audio stack;
  • networking;
  • removable storage and devices;
  • the user's session and environment;
  • host commands, through a helper that reaches back out.

Those holes are not a compromise or a leak. They are the entire product. A normal container feels foreign on a desktop precisely because it cannot see your files or your display. Distrobox is the argument that for development, on your own laptop, you want a container with the isolation turned down.

Where things ended up living

Once I stopped fighting, the division of labour got obvious:

ComponentResponsibility in my setup
BluefinBoots the machine, owns the desktop, hardware, updates, and the session
Linux kernelSchedules processes, controls memory, networking, filesystems, devices — for host and box
Podman (rootless)Creates and runs the OCI container using kernel isolation primitives
DistroboxConfigures the container and wires it into the host desktop and user environment
Ubuntu imageSupplies apt, Ubuntu libraries, and the user space every install script expects
HomebrewHost-level CLI tools that don't deserve a container
claude-boxWhere Claude Code and the project toolchain actually run

My host now has exactly one layered package: my terminal. Everything else either comes with the image, comes from brew, or lives in a box. That single layered package is the honest measure of whether I understood the model — a year ago that list would have had thirty entries on it.

Bluefin stays stable. Ubuntu stays disposable. My project files belong to neither and are visible to both.

The architecture, layer by layer

The clearest way to see the system is to follow a command from the desktop down to the kernel and back.

Bluefin desktop session
│
├── Home directory and project files
├── Wayland/X11, audio, network, devices
│
└── Distrobox command and exported application launcher
    │
    └── Podman (rootless)
        │
        └── Ubuntu container
            ├── Ubuntu filesystem and apt packages
            ├── Shell, runtimes, libraries, developer tools
            └── Claude Code / application process
                │
                └── Uses host integrations exposed by Distrobox

Every box depends on the layer below it, but ownership stays clear.

Bluefin is the host

Bluefin owns the real machine. It starts the kernel, creates the graphical session, manages the hardware, mounts the filesystems. A Distrobox cannot boot on its own because it is not a complete machine.

This is why running an Ubuntu box does not turn my computer into Ubuntu. The Ubuntu release describes the container's user space — its binaries, libraries, config defaults, and repositories. The kernel is still the one Bluefin booted. On an ostree system you can even see the seam in the filesystem layout: my home is /var/home/nikhil, not /home/nikhil, because /home is a symlink on an image-based host.

Podman is the container engine

Distrobox does not implement containers from scratch — it delegates. Podman creates the OCI container and asks the kernel for the boundaries: namespaces for process, mount, and network views; cgroups for resource limits; an image for the root filesystem. Exactly the machinery from the Docker post, invoked by a different front end.

Rootless means Podman runs the container as my regular user instead of through a permanent root-owned daemon. That genuinely reduces the container engine's privileges. It does not make a heavily integrated box a sandbox, and I'll come back to that.

The Ubuntu image supplies user space

The image is what makes the environment feel like Ubuntu: /usr/bin tools, Ubuntu libraries, apt and its repositories, the expected filesystem layout.

When I apt install something inside the box, it writes to the container's storage — not to Bluefin's base image. That is the mutable workspace I was trying to carve out of my host for a week, except now it costs nothing and no reboot.

The container does not bring its own kernel. A kernel module, a low-level driver, or a feature the Bluefin host doesn't have cannot be conjured by installing an Ubuntu package in the box. This is the same shared-kernel tradeoff that makes containers start in milliseconds while VMs take minutes.

Distrobox builds the integration layer

This is the part that is actually Distrobox's own work — mounts, environment variables, sockets, user mappings, and helpers that connect the two worlds:

Ubuntu process        Connection                 Bluefin resource
---------------       ----------------------     --------------------------
opens ~/project   →   mounted home directory  →  the same host project
draws a window    →   Wayland/X11 socket      →  Bluefin desktop compositor
plays audio       →   audio socket/session    →  host speakers
makes a request   →   container networking    →  host network path
opens a device    →   exposed device access   →  hardware managed by host
launches an app   ←   exported .desktop file  ←  Bluefin application menu

These are connections to the real resources, not copies of them. That is why a file edited inside the box changes for the host immediately — there is no sync step, because there is only one file.

How the Claude Code workflow crosses the boundary

This is where this post meets the Claude Code habits I wrote about earlier. All of that advice — run from the project root, /init a CLAUDE.md, keep it short — assumes Claude can see your project. The box does not complicate that at all, and it took me a while to trust it.

The flow:

  1. I enter the Ubuntu box from a Bluefin terminal, or launch an exported desktop entry.
  2. Distrobox asks Podman to start the container if it is stopped.
  3. distrobox-enter starts the process inside the container with the integrated environment.
  4. Claude runs against Ubuntu's libraries and developer tools.
  5. Claude reads and modifies the repository through the shared home mount.
  6. Bluefin sees those changes instantly, because there is one project directory, not two.
  7. Any window it opens reaches Bluefin's display server through the exposed socket.

CLAUDE.md lives in the repo. The repo lives in the shared home. So the memory file, the git history, and my SSH config were never on the wrong side of the boundary — which is exactly why moving into a container didn't cost me the workflow.

If a graphical app is exported with distrobox-export, Distrobox writes a host launcher whose command is really a distrobox-enter ... -e .... The icon sits in Bluefin's menu; the binary and its dependencies live in Ubuntu:

Click in Bluefin
    → host .desktop launcher
        → distrobox-enter
            → Podman starts/enters Ubuntu
                → application runs with Ubuntu libraries
                    → window appears in Bluefin

The window belongs to the Bluefin session. The process belongs to the Ubuntu container. The files belong to my home directory. Three owners, one apparently ordinary application.

What this actually solved

It stopped the host from accumulating. Node, Python, compilers, native libraries, CLIs, build tools — all of it churns inside Ubuntu instead of being layered into Bluefin. The host stays close to the image it is supposed to be. I can delete the box and rebuild it without reinstalling my operating system.

It gave tools the ecosystem they were written for. apt, familiar package names, the expected layout. Compatibility through user space. It works when the requirement is packages and libraries; it does nothing when the requirement is a kernel feature or an unsupported driver.

It avoided a VM. A virtual machine brings its own kernel and virtualized hardware — a stronger boundary, but with memory, disk, startup, and integration costs, plus project files stranded on a separate virtual disk. Sharing the host kernel means processes start immediately and GUI apps sit beside native ones.

It contains dependency conflicts. Different projects can get different boxes with different base images. An experiment that wrecks one container's package state does not touch another box or the host. Not perfect reproducibility — the shared home still carries dotfiles and caches between environments — but a real boundary for system dependencies.

What it does not solve

The same holes in the walls that make this work are exactly what limit it. I would rather be clear about this than sell the setup.

It is not a security sandbox

Distrobox's own documentation says isolation is not a goal. A box that can reach my home directory, display session, and devices has access to everything that matters on this machine.

I treat code inside the box the way I treat code installed for my user account — because that is functionally what it is. Rootless Podman helps. It does not make untrusted code safe, and sudo inside the box is not a meaningful boundary.

The shared home is shared state

Sharing HOME is why my repos and SSH config just work. It is also why the host and the box write the same dotfiles and caches. A package installed in Ubuntu can drop a config file that a Bluefin application then reads, and two distributions do not always agree on that file's format. Distrobox can give a box its own home — at the cost of the seamlessness that was the point.

The container follows the host kernel

Kernel behaviour, security modules, device support, and low-level networking all come from Bluefin. Ubuntu user-space tools report on Bluefin's kernel. This is not a VM and cannot pretend to be one.

GUI and hardware integration have edges

Most desktop applications work because the display and audio sockets are shared. GPU acceleration, portals, keyrings, credential stores, and notifications cross more complicated boundaries — and on a machine with proprietary-adjacent graphics drivers, "which side owns the GPU" becomes a question you will eventually have to answer.

When something breaks, the useful question is always: which layer owns the failing resource?

  • Missing library or binary → Ubuntu.
  • Container lifecycle or mount problem → Distrobox and Podman.
  • Kernel, driver, or physical device → Bluefin.
  • Window, audio, or session problem → the integration socket and host desktop.
  • Wrong or missing project file → the shared-home path and permissions.

That map is the single most useful thing I got out of the whole month. Before I had it, I debugged by applying random fixes in whichever layer I happened to have a terminal open in.

Container, VM, or host package?

RequirementBest starting point
A mutable Ubuntu CLI and GUI development environmentDistrobox
Strong isolation for untrusted softwareA purpose-built sandbox or a VM
A different kernel, or kernel-level testingVM or separate machine
A tightly host-integrated desktop applicationFlatpak or supported host packaging
A reproducible application serviceA conventional OCI container
Fast access to host projects with distro-specific toolsDistrobox

Distrobox sits in the middle: more separation than installing everything on the host, more integration than a normal container, less isolation than a VM. Most of my early mistakes were picking a row and then using the wrong tool for it.

The mental model I kept

I stopped thinking of the Ubuntu box as a second computer. It is a replaceable development user space attached to my Bluefin session.

Bluefin owns the machine.
Podman owns the container lifecycle.
Distrobox owns the bridges.
Ubuntu owns the development packages.
My home directory connects the work.

The thing I actually learned was not about Distrobox. It was that "install it on the machine" is a habit, not a requirement — one I had never questioned because every Linux system I'd used before rewarded it. Bluefin refused, I spent a week arguing, I spent a month taking a detour through Arch, and the answer turned out to be the boring container running the boring distro.

The convenience is not magic and it is not free isolation. It is architecture: each layer owns one job, and the connections between them — the holes in the walls — are the whole reason the workflow feels ordinary.
