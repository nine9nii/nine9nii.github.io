Java to Python for Coding Interviews, Part 1: Types and OOP

Nikhil Shinde|April 23, 2026|10 min read

A practical map from Java to Python: types, interview pitfalls, and object-oriented concepts side by side.

I've written Java for a while, and it's still the language I think in. But for coding interviews, Python is hard to beat: less ceremony, fewer lines, and more of the 45 minutes spent on the actual problem.

The trick is not learning Python from scratch. It's building a mapping from what I already know in Java to the Python equivalent — and learning exactly where the mapping breaks.

This part covers:

  1. Java types → Python types, including the traps
  2. Java OOP → Python OOP, using one class example that brings the main concepts together

Part 2 covers data structures: arrays, hash maps, heaps, linked lists, TreeMap, and recursion.

The mental shift: values have types, variables don't

Gotcha 3: == vs is

Java's == compares references for objects, so you use .equals() for strings. Python flips that:

JavaPython
Same valuea.equals(b)a == b
Same objecta == ba is b

Use == for comparing values (including strings) and reserve is for None: if node is None.

Access modifiers are conventions

Python has no private. A single underscore (_name) means "internal, please don't touch". A double underscore (__color) triggers name mangling — it's stored as _Shape__color — which prevents accidental clashes in subclasses but doesn't stop a determined caller. In practice: use _name and move on.

@property replaces getters and setters

In Java you write getColor() from day one in case you need validation later. In Python you start with a plain attribute (self.color = color) and only upgrade to @property when you need logic. Callers don't change — shape.color = "red" still works, but now runs the setter.

Notice the constructor assigns self.color = color, which goes through the setter, so validation runs on construction too.

Defining area(self) and then area(self, scale) doesn't overload; the second replaces the first. Use default or keyword arguments instead:

__eq__ and __hash__ travel together

Same contract as Java: equal objects must have equal hashes. Python enforces it a little more aggressively — if you define __eq__ without __hash__, instances become unhashable and can't go in a set or be dict keys.

Our Circle hash depends on _radius. Treat that attribute as immutable after construction: changing it while the object is in a set or used as a dictionary key can make the object impossible to find. Python's underscore is a convention, so it does not enforce this for us.

__lt__ is your Comparable

sort(), sorted(), min(), max(), and heapq all use <. Defining __lt__ alone is enough for sorting. This becomes important in Part 2 when we put custom objects into a heap.
