Why Rust? Day 1 of Learning Rust

Nikhil Shinde|November 4, 2026|5 min read

Starting Rust after C++, Java, Go, and Python: a first look at compilation, memory safety, and garbage collection.

Why Rust

After using Java, Python, Golang and C++, I thought I should give Rust a try, the new language that everyone seems to be using everywhere.

Well, tbh my first language was C++. My first choice for building servers and applications is Golang, and for AI it's Python.

I have started my winter arc to learn it inside out and understand the hype around it. It solves a lot of problems that other languages seem to have, including Golang.

Compilation

Rust compiles through LLVM, and compilation is slower than Golang.

  • LLVM does a lot of optimization work, and that takes time.
  • Generics get a separate copy for each concrete type (monomorphization), so there is more code to compile.
  • Go has its own compiler and was built for fast builds.

So I wait longer at compile time, but I get a heavily optimized binary.

Memory safety

  1. Null pointer dereference: the pointer doesn't contain a valid address, yet the program tries to dereference it.
    • In Rust: safe references can't be null. A value that might be missing is an Option<T>, and I have to handle the None case.
  2. Double free: trying to free the same memory twice.
    • In Rust: every value has one owner, and it gets dropped once.
  3. Dangling pointer: a pointer is returned out of its scope and accessed after the memory it points to is gone.
    • In Rust: the borrow checker won't let a reference outlive the value.
  4. Memory leak: memory is allocated on the heap, but I forget to deallocate it. C and C++ are very notorious for this. Usually a GC handles it.
    • In Rust: memory is freed automatically when its owner goes out of scope. Leaks are still possible though, for example an Rc reference cycle, and Rust counts that as memory safe.
  5. Use after free: trying to use the pointer after the memory is freed.
    • In Rust: same story, ownership and the borrow checker catch this at compile time.
  6. Data races: these occur while writing concurrent and multithreaded code. Two or more threads access the same memory, at least one writes, and at least one access is unsynchronized.
    • In Rust: safe Rust doesn't allow them. Deadlocks and other race conditions can still happen.

All of the Rust guarantees above are for safe Rust. unsafe code can break them.

Garbage collection

The JVM, the JavaScript runtime Node.js and the Python environment are literally running a GC behind the scenes to deallocate things. This adds latency. The GC does passes that take milliseconds, and for the computer world that is a lot.

Rust doesn't use a garbage collector. It doesn't contain one, so there are no passes and no CPU use for garbage collection. It handles this gracefully.

GC terms to remember: mark-sweep, tri-color marking, stop the world, generational GC, ZGC and Green Tea.

  • GHz: clock speed in billions of cycles per second. 2 GHz is 2 billion cycles per second, so even 1 ms is 2 million cycles. That's why a pause of a few milliseconds is a lot in the computer world.
  • Java: my notes had passes of around 200 ms, but pause time depends on the collector. G1, the default, ranges from milliseconds to seconds. ZGC pauses are typically under 1 ms.
  • Go: my notes had passes of 10-20 ms, but pauses are typically under 1 ms. The GC still costs CPU though, even when the pauses are small.
  • Rust: no GC pauses and a smaller memory footprint. That helps with startup time and makes services cheaper to run.

A small Rust service can run on something like 32 MB of RAM and 1/20th of a CPU, but it depends on what the service does.

Which language uses what

LanguageGC?Algorithm
Java (HotSpot)YesG1 by default: generational and region-based. Serial, Parallel, ZGC and Shenandoah are also options.
GoYesConcurrent, non-moving, tri-color mark-sweep. Green Tea is the default since Go 1.26.
Python (CPython)YesReference counting, plus a generational GC to clean up reference cycles.
JavaScript (V8, Node.js)YesGenerational. Scavenger (copying) for the young generation, Mark-Compact with concurrent marking for the whole heap.
C / C++NoManual memory management. C++ can also free memory automatically with RAII and smart pointers.
RustNoOwnership. Memory is freed when the owner goes out of scope. Rc and Arc add reference counting when I need shared ownership.

Real systems

  • Kafka: built with Java and Scala.
  • Redpanda: the core is C++ on the Seastar framework. Rust only shows up in small parts, such as the data transforms SDK.
  • NATS.io: uses Golang.

Rust is also well suited for embedded devices.

Why Kafka needs more memory

Kafka runs on the JVM, so I have to budget for the runtime as well as the data.

  • JVM heap: a production broker commonly runs with around 6 GB. The GC also needs room to work, so the heap can't be sized tightly around the live data.
  • Outside the heap: the JVM also uses memory for metaspace, the code cache, thread stacks, direct buffers and GC data. So the real usage can be higher than -Xmx.
  • OS page cache: this is the big one, and it isn't a JVM cost. Kafka keeps recent data in the page cache so consumers can read from memory. At 20 GB written per hour, letting consumers fall 3 hours behind means reserving 60 GB.

Redpanda removes the JVM and GC overhead, but it still isn't small. It needs at least 2 GB per core and 2 MB per partition replica, so an 8-core broker needs at least 16 GB.
