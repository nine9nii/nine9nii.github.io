Building the ls Command in Go

Nikhil Shinde|April 16, 2026|7 min read

Rebuilding a tiny ls from scratch to learn Go's toolchain, os.Args, flag parsing by hand, and reading directories — bugs included.

The fastest way I know to learn a language is to rebuild a tool I already use every day. ls is perfect for that: everyone knows what it should print, it touches the filesystem, and it needs just enough argument parsing to be interesting without being a chore.

Why Go feels small

Go has 25 keywords. That's the whole reserved vocabulary — func, if, for, switch, range, go, defer, chan, and a handful more. There is no while (it's just for), no class, no try/catch.

Rob Pike's essay title sums up the philosophy: "Less is exponentially more." Fewer features means fewer ways to write the same thing, which means code from a stranger reads a lot like code you wrote yourself. You notice this quickly when building a CLI — there is usually one obvious way to do each step.

Step 2: listing a directory

os.ReadDir does the heavy lifting. It returns a slice of os.DirEntry values, already sorted by filename, plus an error:

Two Go habits show up immediately:

  • Errors are values. No exceptions — the function hands you an err, and you check it right there. It's verbose, but you always see where failure is handled.
  • Errors go to stderr. fmt.Fprintln(os.Stderr, ...) keeps error output separate from normal output, so myls nope | wc -l doesn't count the error message as a file. Then exit with a non-zero status so scripts can detect the failure.

Step 4: parsing flags by hand

Go has a flag package, but it doesn't support combined short flags like -la, and doing it by hand teaches more. The rule is simple:

  • If an argument doesn't start with -, it's the path.
  • If it does, every character after the - is a separate flag.

A few things worth pointing out:

  • range over a string yields runes (Unicode code points), so char is compared against rune literals like 'a'.
  • Go's switch doesn't fall through by default. No break needed.
  • The usage message uses Fprintf, not Fprintln. Println doesn't interpret %s — it would print the format string literally. go vet catches this mistake, which is a good reason to run it often.

Step 6: long format with -l

For -l we need metadata: permissions, size, and modification time. os.Lstat returns an fs.FileInfo with all three. (Lstat rather than Stat so a symlink reports itself instead of the file it points to — same as the real ls.)

Two nice surprises here:

  • info.Mode() already prints as -rw-r--r-- / drwxr-xr-x. No bit twiddling required.
  • Go formats time with a reference date instead of %Y-%m-%d codes. The reference is Mon Jan 2 15:04:05 MST 2006, so you write the layout by example: "Jan _2 15:04" means "short month, space-padded day, 24h time".

Where this version stops

This is a learning project, not a complete replacement for ls. It accepts one directory (if you supply several, the last one wins), does not implement --, and treats arguments beginning with - as flags. Use a path such as ./-notes for a directory whose name begins with a dash. A metadata error is printed but does not currently change the final exit status. Real ls also has richer formatting, sorting, and handling for individual files.

What I took away

  • Read the docs first. go doc os.Args would have saved me the os.Args[0] bug in five seconds.
  • Run go vet. It catches Println with format verbs and other suspicious patterns; the compiler itself rejects unused local variables and imports.
  • Keep one source of truth. The worst bug here wasn't a typo; it was two pieces of code both deciding what path should be.
  • Small language, fast progress. Without classes, exceptions, or inheritance to think about, nearly all of the effort went into the problem itself.

Next steps if you want to keep going: multiple path arguments, -h for human-readable sizes, coloring directories, or listing in columns based on terminal width.
